3. Phase 2: Create the ARM Instance

PHASE 2 — Instance Creation (15 minutes + capacity wait)
1 Navigate to Compute

In Oracle Cloud Console: hamburger menu (top-left) → Compute → Instances → Create Instance

2 Configure the Instance

Name & Compartment

  • Name: ollama-arm (or whatever you like)
  • Compartment: Leave as default (root compartment)

Placement

  • Availability Domain: Try AD-1 first. If "Out of capacity", try AD-2 or AD-3.

Image and Shape

  • Click Change Image
  • Select Canonical Ubuntu 22.04 (or 24.04)
  • Make sure it says aarch64 (ARM)
  • Click Change Shape
  • Select shape series: Ampere
  • Select shape: VM.Standard.A1.Flex
  • Set Number of OCPUs: 4
  • Set Amount of memory (GB): 24
This maxes out the free tier allocation. You can split it (e.g., 2 instances with 2 OCPU / 12 GB each) but one big instance is better for running larger models.

Networking

  • Select or create a VCN (Virtual Cloud Network)
  • Use a public subnet
  • Check Assign a public IPv4 address

SSH Keys

  • Select Generate a key pair for me
  • Download BOTH the private key (.key) and public key (.pub)
  • Save them somewhere safe — you can't download again!
On iPhone: Download the keys to Files app. You'll reference the private key path when SSHing. Alternatively, paste your existing EC2 SSH public key to reuse the same key.

Boot Volume

  • Expand Boot volume section
  • Check Specify a custom boot volume size
  • Set to 200 GB (free tier allows up to 200 GB total)
3 Click "Create"

If successful, the instance will start provisioning. Note the Public IP Address once it appears — you'll need it.

Dealing with "Out of Capacity" Error

This is the most common issue. Oracle's ARM instances are very popular because they're free. If you see "Out of capacity for shape VM.Standard.A1.Flex", don't panic — there are workarounds.
Strategy 1: Try Different Availability Domains

Each region has 1-3 Availability Domains (AD-1, AD-2, AD-3). Capacity varies per AD. Try each one.

Strategy 2: Try a Smaller Config First

Start with 2 OCPU / 12 GB RAM — smaller shapes have better availability. You can resize later (scale up to 4/24 when capacity opens).

Strategy 3: Try Off-Peak Hours

Best times to try (in UTC): 03:00-07:00 (early morning Americas) or 14:00-17:00 (early morning Asia-Pacific).

Strategy 4: Automated Retry Script (Recommended)

Use the community retry tool that automatically retries instance creation until capacity opens:

  1. Go to github.com/hitrov/oci-arm-host-capacity
  2. Follow the setup instructions (needs OCI CLI config)
  3. Run it and leave it retrying — usually succeeds within hours to a day
How to set up the retry script

On your EC2 instance (or any machine with Python):

# Install OCI CLI
pip3 install oci-cli

# Configure OCI CLI with your Oracle Cloud credentials
oci setup config
# It will ask for:
#   - User OCID (Profile > User Settings > OCID)
#   - Tenancy OCID (Administration > Tenancy Details > OCID)
#   - Region (e.g., eu-frankfurt-1)
#   - Generate new API key? Yes
#   - Upload the public key to Oracle Cloud Console
#     (Identity > Users > Your User > API Keys > Add API Key)

# Clone the retry script
git clone https://github.com/hitrov/oci-arm-host-capacity.git
cd oci-arm-host-capacity

# Edit .env with your instance details:
#   OCI_SHAPE=VM.Standard.A1.Flex
#   OCI_OCPUS=4
#   OCI_MEMORY_IN_GBS=24
#   OCI_SUBNET_ID=ocid1.subnet...
#   OCI_IMAGE_ID=ocid1.image...
#   OCI_AVAILABILITY_DOMAIN=xxxx:EU-FRANKFURT-1-AD-1

# Run it
python3 oci_arm.py

It retries every 60 seconds. Let it run until it succeeds.

Strategy 5: Change Home Region (Last Resort)

If you just created your account (within a few hours), you might be able to contact Oracle support to change your home region. After that window closes, you'd need a new account. Try Frankfurt first.

4. Phase 3: Network Security Rules

PHASE 3 — Firewall / Network (5 minutes)

Oracle Cloud has TWO layers of firewall: Security Lists (cloud-level) and iptables/UFW (OS-level). Both must allow traffic. The setup script handles OS-level. You configure cloud-level here.

1 Find Your Instance's Subnet
  1. Go to your instance details page
  2. Under Primary VNIC, click the Subnet link
  3. Click the Security List that's attached (usually "Default Security List")
2 Add Ingress Rules

Click Add Ingress Rules and add these two rules:

RuleSource CIDRProtocolPortDescription
SSH 0.0.0.0/0 TCP 2222 SSH on custom port
Ollama YOUR_EC2_ELASTIC_IP/32 TCP 11434 Ollama API (EC2 only)
Replace YOUR_EC2_ELASTIC_IP with your actual EC2 Elastic IP. The /32 means "only this one IP". This ensures only your EC2 can reach Ollama.

Find your EC2 IP: In AWS Console → EC2 → Elastic IPs, or from the EC2 instance run: curl -s http://checkip.amazonaws.com
3 Verify Default Egress Rule

The default egress rule should already allow all outbound traffic (0.0.0.0/0, All Protocols). If it's missing, add it — Ollama needs outbound access to download models.

5. Phase 4: First SSH & Setup Script

PHASE 4 — Server Setup (20 minutes, mostly waiting for model downloads)
1 SSH Into the Oracle Instance

The default user on Oracle Ubuntu is ubuntu:

Desktop

chmod 400 ~/path/to/oracle-key.key
ssh -i ~/path/to/oracle-key.key ubuntu@ORACLE_PUBLIC_IP

iPhone (Termius/Prompt app)

  • Import the .key file into your SSH app
  • Connect to ORACLE_PUBLIC_IP port 22 as user ubuntu
2 Clone the Repo 
sudo apt-get update && sudo apt-get install -y git
sudo git clone https://github.com/in-fused/VPS.git /home/VPS
cd /home/VPS
3 Run the Oracle Setup Script

Replace EC2_ELASTIC_IP with your actual EC2 Elastic IP:

sudo bash scripts/setup-ollama-server.sh EC2_ELASTIC_IP

For example:

sudo bash scripts/setup-ollama-server.sh 54.123.45.67

The script will:

  1. Update system packages
  2. Create deploy user with sudo + SSH keys
  3. Harden SSH (port 2222, key-only, no root)
  4. Configure UFW (SSH + Ollama from EC2 IP only)
  5. Set up Fail2Ban
  6. Create 4 GB swap
  7. Install Ollama natively (not Docker — better ARM performance)
  8. Configure Ollama for remote access (0.0.0.0:11434)
  9. Pull 3 recommended models:
ModelSizePurposeDownload Time
qwen3.5:9b~6 GBGeneral purpose + agent tasks (beats GPT-OSS-120B)~3 min
qwen3:14b~9 GBReasoning + general purpose (dense)~5 min
qwen3-coder:30b-a3b~18 GBCoding (MoE, 3.3B active — best open-source)~10 min
Don't close the SSH session during model downloads! If your session drops, reconnect and check status with ollama list. You can re-pull any model that didn't finish: ollama pull qwen3-coder:30b-a3b
4 Verify Ollama is Running 
# Check service status
sudo systemctl status ollama

# List downloaded models
ollama list

# Quick test
ollama run qwen3.5:9b "Say hello in one sentence" --verbose
5 Note the SSH Change

SSH port is now 2222. Reconnect with:

ssh -i ~/path/to/oracle-key.key -p 2222 deploy@ORACLE_PUBLIC_IP

6. Phase 5: Connect to EC2 Hub

PHASE 5 — Wire It Up (5 minutes)

Now connect your EC2 hub to the Oracle Ollama server so LiteLLM can route requests to local models.

1 Update .env on EC2

iOS/SSM

cd /home/VPS && sudo sed -i 's|^OLLAMA_BASE_URL=.*|OLLAMA_BASE_URL=http://ORACLE_PUBLIC_IP:11434|' .env && grep OLLAMA .env

Desktop/SSH to EC2

cd /home/VPS
nano .env
# Set: OLLAMA_BASE_URL=http://ORACLE_PUBLIC_IP:11434
Replace ORACLE_PUBLIC_IP with your actual Oracle instance's public IP address.
2 Restart the Stack on EC2

iOS/SSM

cd /home/VPS && sudo docker compose down && sudo docker compose up -d && sleep 15 && sudo docker compose ps

Desktop/SSH

cd /home/VPS
sudo docker compose down
sudo docker compose up -d
sleep 15
sudo docker compose ps
3 Verify LiteLLM Sees Ollama Models 
sudo docker compose exec litellm curl -s http://localhost:4000/v1/models \
  -H "Authorization: Bearer $(grep LITELLM_MASTER_KEY .env | cut -d= -f2)" \
  | python3 -c "import sys,json; [print(m['id']) for m in json.load(sys.stdin)['data']]" \
  | grep -i 'llama\|qwen\|deepseek'

You should see the Ollama models listed (e.g., qwen3.5:9b, qwen3:14b, qwen3-coder:30b).

PHASE 6 — End-to-End Test (5 minutes)
1 Test from EC2 (Direct) 
# Test Ollama connectivity from EC2
curl -s http://ORACLE_PUBLIC_IP:11434/api/tags | python3 -m json.tool
2 Test via LiteLLM (Through the Stack) 
MASTER_KEY=$(grep LITELLM_MASTER_KEY /home/VPS/.env | cut -d= -f2)
curl -s https://in-fused.org/api/litellm/v1/chat/completions \
  -H "Authorization: Bearer $MASTER_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"qwen3.5:9b","messages":[{"role":"user","content":"Write a hello world in Python"}],"max_tokens":50}'
3 Test from Mission Control
  1. Open https://in-fused.org/workspace/
  2. Start a new chat with any agent
  3. The agent should be able to use Ollama models as fallbacks
  4. Or go to the landing page (https://in-fused.org/) and use Quick Chat with a local model
If all tests pass: Your Oracle ARM server is live and connected. LiteLLM will automatically route requests to Ollama models when selected, and use them as part of the fallback chain. The models run 24/7 with no API costs.

8. Managing Models

SSH into the Oracle instance to manage models:

ssh -i key.pem -p 2222 deploy@ORACLE_PUBLIC_IP

Installed Models (24 GB RAM)

ModelSize (Q4)RAM NeededGood ForSpeed (est.)
qwen3.5:9b~6 GB~8 GBGeneral + agent tasks, tool calling~8 t/s
qwen3:14b~9 GB~12 GBReasoning, general purpose (dense)~5 t/s
qwen3-coder:30b-a3b~18 GB~20 GBCoding (MoE, 3.3B active per token)~3 t/s

Optional Models (can be pulled manually)

ModelSizeRAM NeededGood For
qwen3:8b~5 GB~7 GBLighter alternative to 14B
qwen3.5:4b~3 GB~4 GBUltra-fast, simple tasks
qwen3-coder-next~46 GB~48 GBBest coding model (won't fit in 24GB)
Memory rule of thumb: Model file size × 1.3 = approximate RAM needed while running. Ollama loads one model at a time by default (OLLAMA_MAX_LOADED_MODELS=1). Only the active model uses RAM — inactive models stay on disk (200 GB). The MoE coder model (30B) only activates 3.3B params per token, so despite its large file size it runs with reasonable efficiency on ARM CPU.

Model Management Commands

# List installed models
ollama list

# Pull a new model
ollama pull codestral:22b

# Remove a model (to free disk space)
ollama rm model-name

# Test a model interactively
ollama run qwen3.5:9b "Explain Docker networking"

# Check disk usage
df -h /

# Check model storage size
du -sh /usr/share/ollama/.ollama/models/

After Adding/Removing Models

LiteLLM auto-discovers Ollama models. If you add a new model to Ollama, you may need to add a matching entry in litellm_config.yaml on EC2 and restart LiteLLM:

iOS/SSM (on EC2)

cd /home/VPS && sudo docker compose restart litellm && sleep 10 && sudo docker compose logs --tail=20 litellm

9. Elite Agent Onboarding

When an agent earns Elite tier through the governance system (weekly champion), they gain access to the Oracle partition.

What Elite Agents Get

  • Access to local models (no API costs, no rate limits)
  • Persistent storage on the Oracle server
  • Background job capability via cron
  • Can bring team members onto Oracle alongside them
  • Can request new specialist agents

How It Works

  1. Governance system tracks agent performance (success rate, quality, efficiency, streaks)
  2. Weekly champion earns Elite tier automatically
  3. Elite agent's model assignment can be switched to an Ollama model for cost-free operation
  4. Owner can manually promote sustained Elite performers to Manager (above both teams)
Current implementation: Elite tier Oracle access is managed manually by the owner. The governance system identifies the champion; the owner updates the agent's model assignment in Mission Control or the OpenClaw config to use Ollama models.

10. Maintenance & Troubleshooting

Routine Checks

# On Oracle instance:
sudo systemctl status ollama     # Service status
ollama list                      # Installed models
df -h /                          # Disk usage
free -h                          # Memory usage
htop                             # Live resource monitor

Common Issues

EC2 can't reach Ollama
  1. Check Oracle Security List has ingress rule for EC2 IP on port 11434
  2. Check UFW on Oracle: sudo ufw status (should show 11434 from EC2 IP)
  3. Check Ollama is listening: sudo ss -tlnp | grep 11434
  4. Test locally on Oracle: curl http://localhost:11434/api/tags
Ollama is slow / models take long to respond
  • Check if model is still loading: first request after idle takes longer (cold start)
  • Check memory pressure: free -h (swap usage > 2 GB = too many models loaded)
  • Reduce to 1 loaded model: OLLAMA_MAX_LOADED_MODELS=1 (already set by script)
  • Use smaller quantization: ollama pull qwen3:14b-q4_K_M
Ollama crashed / not responding 
sudo systemctl restart ollama
sudo journalctl -u ollama --since "5 min ago"
Disk full on Oracle 
# Check what's using space
du -sh /usr/share/ollama/.ollama/models/blobs/* | sort -rh | head -10

# Remove unused models
ollama rm model-name

# Clean apt cache
sudo apt-get clean
EC2 IP Changed (Elastic IP released)

If your EC2 Elastic IP changes, update both:

  1. Oracle Security List: Edit the Ollama ingress rule with new EC2 IP
  2. Oracle UFW: SSH in and update the firewall rule:
sudo ufw delete allow from OLD_EC2_IP to any port 11434
sudo ufw allow from NEW_EC2_IP to any port 11434 proto tcp comment "Ollama from EC2"

Updating Ollama

# On Oracle instance:
curl -fsSL https://ollama.com/install.sh | sh
sudo systemctl restart ollama
ollama --version
