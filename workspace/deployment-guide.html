1. Architecture Overview

3. Provision EC2 Instance

1 Launch EC2 Instance
  • Instance type: t3.small (2 vCPU, 2 GB RAM) — ~$25/month
  • AMI: Ubuntu 22.04 LTS (or 24.04)
  • Storage: 30 GB gp3 (minimum, 20 GB will be too tight)
  • Security Group: Allow inbound ports 80 (HTTP), 443 (HTTPS), 2222 (SSH)
  • Key Pair: Create or select an SSH key pair
2 Enable SSM for Mobile Access (Recommended)
  • Attach the IAM role AmazonSSMManagedInstanceCore to the instance
  • Install the SSM agent (pre-installed on Ubuntu AMIs)
  • Install the AWS Console app on iPhone for mobile management
3 Allocate Elastic IP

Allocate an Elastic IP and associate it with your instance. This gives you a static IP that persists across stops/starts.

4. Server Hardening & Docker

SSH into your new instance and run the setup script. It handles everything: system updates, SSH hardening, firewall, Docker, swap, and security patches.

1 Initial SSH Connection 
ssh -i your-key.pem ubuntu@YOUR_ELASTIC_IP
2 Clone the Repository 
sudo apt-get install -y git
sudo git clone https://github.com/in-fused/VPS.git /home/VPS
cd /home/VPS
3 Run Server Setup 
sudo bash scripts/setup-server.sh

This script performs:

  • System update & essential packages
  • Creates deploy user with sudo + SSH keys
  • SSH hardening: port 2222, key-only, no root login
  • UFW firewall: allow 2222, 80, 443 only
  • Fail2Ban: ban after 3 failed SSH attempts
  • Docker + Docker Compose installation
  • 4 GB swap space (critical for t3.small)
  • Unattended security upgrades
  • Docker log rotation (10 MB max per container)
Do NOT close your current SSH session! Open a NEW terminal and verify SSH on port 2222 works before closing the original connection:
ssh -i your-key.pem -p 2222 deploy@YOUR_ELASTIC_IP

5. Domain & DNS Setup

1 Point Domain to EC2

In your DNS provider (Route 53, Cloudflare, Namecheap, etc.), create an A record:

TypeNameValueTTL
A@ (root)YOUR_ELASTIC_IP300
2 Verify DNS Propagation 
dig +short your-domain.com

Should return your Elastic IP. May take 5-30 minutes to propagate.

Caddy handles HTTPS automatically. Once DNS points to your server and ports 80/443 are open, Caddy obtains and renews Let's Encrypt certificates without any configuration.

7. Deploy the Stack

1 Run the Deploy Script

Desktop/SSH

cd /home/VPS
sudo bash scripts/deploy.sh

iOS/SSM

cd /home/VPS && sudo bash scripts/deploy.sh

The script will:

  1. Validate .env — checks for at least one API key
  2. Auto-generate secrets — fills any empty keys in .env
  3. Clean old Docker images — frees disk space
  4. Pull pre-built images — LiteLLM, PostgreSQL, OpenClaw
  5. Build custom images — Caddy (with rate-limit), Open WebUI (with theme), Scrapling
  6. Start the stack — docker compose up -d
  7. Health checks — waits for LiteLLM, Open WebUI, OpenClaw
  8. Print status — shows URLs, providers, and useful commands

8. Post-Deploy Verification

1 Check All Services Running 
sudo docker compose ps

All services should show Up (healthy) or Up. The init containers (openclaw-init, workspace-init) will show Exited (0) — that's correct.

2 Verify in Browser
  • Open https://your-domain.com/ — should show login page
  • Log in with OPENCLAW_PASSWORD — should show Open WebUI
  • Open https://your-domain.com/workspace/ — should show Mission Control
  • Open https://your-domain.com/openclaw/ — should show OpenClaw UI
3 Verify LLM Connectivity 
# Check LiteLLM models are loaded
sudo docker compose exec litellm curl -s http://localhost:4000/v1/models \
  -H "Authorization: Bearer $(grep LITELLM_MASTER_KEY .env | cut -d= -f2)" \
  | python3 -m json.tool | head -30
4 Check Logs if Something is Wrong 
# All services
sudo docker compose logs --tail=50

# Specific service
sudo docker compose logs --tail=50 openclaw
sudo docker compose logs --tail=50 litellm
sudo docker compose logs --tail=50 caddy

9. Mobile Access (AWS SSM)

SSM lets you manage the server from the AWS Console iOS app without SSH keys or open ports.

Setup

  1. In AWS Console → IAM → Roles → attach AmazonSSMManagedInstanceCore to your EC2 instance's role
  2. Install the AWS Console app on iPhone
  3. Navigate to Systems Manager → Session Manager → Start a session → select your instance

SSM Gotchas

  • Always run first: sudo git config --global --add safe.directory /home/VPS (SSM runs as ssm-user)
  • Commands must be single-line chained with && (SSM doesn't persist shell state)
  • Always use -y flags — no interactive prompts
  • Sessions time out, but docker compose up -d runs detached — deploys complete even if session drops

Common Mobile Commands

Full deploy from feature branch:

cd /home/VPS && sudo git config --global --add safe.directory /home/VPS && sudo git pull origin main && sudo bash scripts/deploy.sh

Restart all services:

cd /home/VPS && sudo docker compose restart

Check status:

cd /home/VPS && sudo docker compose ps

View logs:

cd /home/VPS && sudo docker compose logs --tail=50

Update a single service (e.g., openclaw):

cd /home/VPS && sudo docker compose pull openclaw && sudo docker compose rm -sf openclaw && sudo docker compose up -d openclaw && sleep 10 && sudo docker compose logs --tail=50 openclaw

10. Mission Control Quick Start

Mission Control is the custom SPA at /workspace/ for managing agents, chat, and workflows. It works as a mobile PWA.

1 Open Mission Control

Navigate to https://your-domain.com/workspace/ and log in with the site password.

2 Start a Chat
  1. Go to Chat in the sidebar
  2. Click New Conversation
  3. Select Lead (the orchestrator agent)
  4. Give Lead a task — it will delegate to the right specialist
3 Install as PWA (iPhone)
  1. Open Mission Control in Safari
  2. Tap the Share button → "Add to Home Screen"
  3. Now it opens full-screen like a native app

12. Maintenance & Operations

Updating the Stack

Full update (pull latest + rebuild + restart):

iOS/SSM

cd /home/VPS && sudo git config --global --add safe.directory /home/VPS && sudo git pull origin main && sudo bash scripts/deploy.sh

Desktop/SSH

cd /home/VPS
sudo git pull origin main
sudo bash scripts/deploy.sh

Free Disk Space

# Remove unused Docker images, containers, build cache
sudo docker system prune -af

# Check disk usage
df -h /

# Find large files
du -sh /var/lib/docker/*

Reset OpenClaw (re-seeds all agents from scratch)

iOS/SSM

cd /home/VPS && sudo docker compose rm -sf openclaw openclaw-init && sudo docker volume rm ai-hub_openclaw-data && sudo docker compose up -d openclaw

View Agent Workspace Files

# List agent workspace directories
sudo docker compose exec openclaw ls -la /home/node/.openclaw/

# Read an agent's soul file
sudo docker compose exec openclaw cat /home/node/.openclaw/workspace-Lead/SOUL.md

Backup

# Backup all Docker volumes
sudo docker compose down
sudo tar czf /tmp/ai-hub-backup-$(date +%Y%m%d).tar.gz \
  /var/lib/docker/volumes/ai-hub_*

13. Troubleshooting

OpenClaw won't start

OpenClaw depends on LiteLLM being healthy. Check LiteLLM first:

sudo docker compose logs --tail=30 litellm
sudo docker compose ps litellm

If LiteLLM is unhealthy, check DB_PASSWORD matches the existing PostgreSQL volume.

Caddy build fails (no space left on device)

The Dockerfile uses a pre-built binary download (no Go compilation needed). If it still fails:

sudo docker system prune -af && sudo docker builder prune -af
df -h /

You need at least ~1 GB free for Docker builds.

WebSocket connection fails

Check that OPENCLAW_ALLOW_INSECURE_PRIVATE_WS=1 is in docker-compose.yml. Also verify:

sudo docker compose logs --tail=20 openclaw | grep -i "gateway\|websocket\|listen"
Chat not streaming / hanging

Caddy must have flush_interval -1 on every proxy handler. Check the Caddyfile:

grep flush_interval Caddyfile
Agents can't use tools (exec, write, edit)

OpenClaw v2026.3.2 changed tools.profile default to "messaging". The entrypoint forces 'full'. Verify:

sudo docker compose exec openclaw cat /home/node/.openclaw/openclaw.json | grep -A2 profile
Rate limits / 429 errors

LiteLLM auto-fallbacks: Groq → Cerebras → DeepSeek. If all free providers are exhausted, requests hit DeepSeek ($0.28/1M). Check rate limit status:

sudo docker compose logs --tail=50 litellm | grep -i "429\|rate\|fallback"
DB_PASSWORD mismatch after volume exists

PostgreSQL only reads the password on first bootstrap. If the volume exists but password changed:

# Option 1: Set the original password in .env
# Option 2: Remove the volume and start fresh
sudo docker compose down
sudo docker volume rm ai-hub_litellm-db-data
sudo bash scripts/deploy.sh
